# 原文疑点（只标注，不修订）

1. **第 4 页对比示例的 Miss 次数不成立。** 原文称在 Build 时改落盘 p1 后，Probe key=0 和 key=3 命中，“仅 PROBE key=2 需加载 p2，Hit=2、Miss=1”。但此前 p2 已在内存，而 p1 已在磁盘，故 PROBE key=1 必须 Miss；四个 Probe 中 Hit=2、Miss=1 的总数也不等于 4。若加载 p1 时落盘 p2，并在后续加载 p2 时落盘 p1、保留 p0，则 Hit=2、Miss=2。这只是一个合法调度分支，不代表改落盘 p1 后结果唯一。

2. **第 2–3、13–14 页的目标分区保护规则没有在参考引擎中实现。** 文字要求 INSERT 溢出时引擎静默忽略对当前目标分区的 SPILL；但第 9 页 `executeActions` 没有接收当前 INSERT 目标，也没有相关检查。朴素调度器自身排除了目标分区，但不能由此保证其他调度器的动作被引擎拦截。此处保留原代码，不尝试利用差异。

3. **“CPU 时间”与实际计时方式不同。** 第 4、14 页称累计回调 CPU 时间，但第 9 页采用 `std::chrono::high_resolution_clock` 的时间差，不是专门的线程/进程 CPU 计时。且 `getSystemState()` 位于被计时 lambda 内，第 8–9 页所示的 `state.operators = operators_` 状态复制也被计入，文字又称框架自身耗时不计入。后续测性能时必须分清规范与实际实现。

4. **第 13 页骨架注释与精确释放量存在措辞差异。** 注释说“须释放至少 tuple_size 字节”，但实际只需释放 `max(0, memory_used + tuple_size - M)`；原文参考基线也是将已有空闲空间计入后补足缺口。

5. **输入中的算子行顺序存在隐含假设。** 第 5 页未明确 K 行须按 op_id 升序给出；第 10 页 `addOperator` 使用 push_back，而其余代码按 op_id 索引 operators。若行序不对应编号可能出现状态错配，实际评测输入是否保证顺序未知。

6. **样例的内存规模是格式演示例外。** 第 5 页一般约束为 M≥64MB，但样例 M=256 字节；保留原样。
